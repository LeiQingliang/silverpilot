# 通用原则

先查询可用目录和 ID，再收集必填信息，然后创建待确认动作。任何时候都不根据名称猜 ID，不用历史订单的地址代替用户本次确认。

# 活动报名

1. 调用可报名活动查询，展示活动 ID、名称和日期。
2. 用户选择后，系统复核活动状态、时间、名额和重复报名。
3. 创建待确认动作；用户确认后才写入报名关系。

# 服务预约

1. 查询已启用的服务小类。
2. 收集服务小类 ID、不早于当天的日期和完整服务地址。
3. 确认卡中地址应遮罩，不在审计列表里展示完整地址。
4. 只有“待受理”的当前用户订单可由用户取消。

# 助餐预订

1. 先查询或按关键词检索已启用菜谱。
2. 收集菜谱 ID、晚于当前时间的用餐时间、1至20人的人数和可选备注。
3. 系统不使用“适合人群”文案代替个体化医疗建议。
4. 只有当前用户的待处理助餐订单可取消。

# 异常分流

- 目录无结果：如实说明，不创建虚假选项。
- 参数不全：一次只追问必要信息。
- 资源状态变更：以执行时复核为准，说明失败原因并让用户重新选择。
- 系统异常：不宣称已完成，保留运行 ID 便于排查。
