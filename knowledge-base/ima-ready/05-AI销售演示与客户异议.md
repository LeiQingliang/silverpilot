# 适用范围

面向社区养老服务机构的一线主管或运营负责人开展模拟售前演练。使用合成居民与演示服务数据。公网共享账号适合展示服务查询，预约写入演示使用本地环境、有写权限的居民账号和已配置的模型。

# 会前确认

- 当前由谁接收预约、核对服务和地址、处理重复申请？哪一步最常需要电话回访？
- 一笔预约何时算办结？请对方指出原流程中可以核对的订单记录，以及需要居民本人确认的字段。
- 若进入试点，由谁记录办理耗时和人工介入？哪些数据允许进入演示环境或发送给模型？

# 八分钟演练建议

1. **查目录。** 请小伴查询可预约的上门服务，核对当前服务目录中的项目。记录所选服务和自己的订单列表，作为操作前基线。
2. **看确认卡。** 在本地提交服务名称、今天或之后的日期和虚构地址。信息齐全后核对确认卡中的服务、日期和地址摘要。`PENDING` 表示等候居民决定。
3. **检验两种选择。** 第一次点「暂不执行」，核对自己的订单列表。另发一笔请求并点「确认并执行」，核对执行结果、订单列表中的新记录与动作历史。若失败，按实际状态讲解，在原因查明前保留失败记录。
4. **按需展示知识依据。** 询问一项已审核的业务规则，核对返回的 `[KB:…]` 与来源。过期文档会被过滤，无匹配时如实说明。运营页面可查看运行次数、成功率、平均延迟和工具调用次数，演示时说明所选时间范围。

# 回应客户异议

| 对方关心的问题 | 可以现场核对的证据 |
| --- | --- |
| “助手说成功了，怎么确认真的约上了？” | 用本次服务和日期匹配当前居民的订单，再查看确认动作的执行状态。聊天措辞、待确认卡都不足以证明预约已办结。 |
| “共享账号可以替别人办事吗？” | 展示公网账号的只读限制。在有写权限的本地环境，仅演示当前居民自己的订单，使用虚构地址。 |
| “能节省多少时间？” | 建议选同一项预约任务，对照原流程与助手流程，记录尝试数、成功订单数、每次用时和人工介入次数。样本规模、起止点和失败口径由试点双方事先约定，收益等实测后计算。 |
